# BigInt — integers with no fixed width, and no mixing with numbers

**Level:** 201 · for anyone whose integers outgrew 2^53

**One line:** `2n ** 64n` is exact and `-7n / 2n` is `-3n`, because division truncates toward zero, but `1n + 1` throws a `TypeError`: arithmetic never mixes BigInt with Number, while comparison does and compares exact values, so `1n == 1` is `true` and `2n ** 53n + 1n == 2 ** 53 + 1` is `false`; a BigInt grows as needed up to V8's ceiling of about 2^30 bits.

**Keywords:** `BigInt`, `BigInt.asIntN`, `BigInt.asUintN`

A BigInt literal is an integer with an `n` after it. The first program puts some BigInt arithmetic beside the same arithmetic on Numbers.

## Reading the output

- **`2n ** 64n` prints all 20 digits of 2^64.** `2 ** 64` prints `18446744073709552000`, although a double holds a power of two exactly (`BigInt(2 ** 64)`, in the conversions below, gets every digit back): Number's `toString` writes the fewest digits that identify the double, and pads the rest with zeros ([ECMA-262 — Number::toString ↗](https://tc39.es/ecma262/#sec-numeric-types-number-tostring)).
- **`2n ** 53n + 1n` is exact and `2 ** 53 + 1` is not.** Past 2^53 a double cannot hold every integer, and 2^53 + 1 rounds to 2^53 ([Safe integers](../../10_Numbers_and_Math/safe_integers/README.md)). A BigInt has no fixed width to run out of: ECMA-262 says a BigInt may be any size ([The BigInt Type ↗](https://tc39.es/ecma262/#sec-ecmascript-language-types-bigint-type)), and V8's ceiling is the subject of the last section.
- **`/` truncates toward zero.** `7n / 2n` is `3n` and `-7n / 2n` is `-3n`: the fraction is dropped, and a floor would have given −4. ECMA-262 defines BigInt division as the quotient truncated ([BigInt::divide ↗](https://tc39.es/ecma262/#sec-numeric-types-bigint-divide)).
- **`%` takes the sign of the dividend**, so `-7n % 2n` is `-1n`, as `-7 % 2` is `-1` for Numbers ([BigInt::remainder ↗](https://tc39.es/ecma262/#sec-numeric-types-bigint-remainder)).
- **Dividing by zero throws** a `RangeError`, where Number division gives `Infinity`.

## Which operations throw when a BigInt meets a Number?

Eleven expressions put a BigInt beside a Number, or hand a BigInt to code that expects a Number.

<!-- source:bigint_mixing_js -->
*[`bigint_mixing_js.js`](examples/bigint_mixing_js.js) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```javascript

// text (a BigInt with its "n"); a thrown error prints as name: message.
const show = (compute) => {
  try {
    const value = compute();
    return typeof value === "bigint" ? `${value}n` : String(value);
  } catch (error) {
    return `${error.name}: ${error.message}`;
  }
};

const cases = [
  ["1n + 1", () => 1n + 1],
  ["1n * 1.5", () => 1n * 1.5],
  ["Math.max(1n, 2n)", () => Math.max(1n, 2n)],
  ["+1n", () => +1n],
  ["-1n", () => -1n],

  ["1n === 1", () => 1n === 1],
  ["2n > 1", () => 2n > 1],
  ["1n < 1.5", () => 1n < 1.5],
  ["Number(1n) + 1", () => Number(1n) + 1],
  ["1n + BigInt(1)", () => 1n + BigInt(1)],
```

- **Arithmetic refuses to mix.** `1n + 1` and `1n * 1.5` throw: ECMA-262 converts both operands of `+`, `*` and the other arithmetic operators to numeric values, and throws a `TypeError` when one is a BigInt and the other a Number ([ApplyStringOrNumericBinaryOperator ↗](https://tc39.es/ecma262/#sec-applystringornumericbinaryoperator)). V8's feature article gives the reason: any implicit conversion could lose information, since a BigInt cannot hold a fraction and a Number cannot hold every integer past 2^53 ([V8 — BigInt ↗](https://v8.dev/features/bigint)).
- **Code that expects a Number refuses a BigInt.** `Math.max(1n, 2n)` throws although both arguments are BigInts, and so does unary `+1n`: both convert with ToNumber, which throws for a BigInt ([ToNumber ↗](https://tc39.es/ecma262/#sec-tonumber), [`Math.max` ↗](https://tc39.es/ecma262/#sec-math.max)). The V8 article says unary `+` was left out so that asm.js code can keep counting on `+x` to give a Number or throw. Unary `-` works and gives a BigInt.
- **Comparison mixes.** `1n == 1`, `2n > 1` and `1n < 1.5` all work, and give the answer the mathematics gives. The V8 article's reason: a comparison returns a boolean, so there is no precision to lose. `1n === 1` is `false`, because `===` never matches two values of different types.
- **Converting is how you mix on purpose.** `Number(1n) + 1` is `2` and `1n + BigInt(1)` is `2n`: you pick the type of the answer, and with it the limits you accept.

## Is `2n ** 53n + 1n == 2 ** 53 + 1` true?

It is `false`, and the reason is on lines 2 and 3. The Number side is computed first, in doubles, and `2 ** 53 + 1` has already rounded to `9007199254740992` when the comparison starts. The comparison then converts neither side: between a BigInt and a Number, `==` and `<` compare the exact mathematical values ([IsLooselyEqual ↗](https://tc39.es/ecma262/#sec-islooselyequal), [IsLessThan ↗](https://tc39.es/ecma262/#sec-islessthan)). 9007199254740993 is not 9007199254740992, so `==` is `false` and `>` is `true`, and `2n ** 53n` equals the rounded Number exactly.

Converting first gives a different answer. `Number(2n ** 53n + 1n)` rounds to the same double, and then the two sides are equal. So a mixed comparison is exact, but it cannot undo rounding that happened while the Number was being computed.

## What `BigInt()` accepts, and what `JSON.stringify` refuses

`BigInt()` on strings and on Numbers, then `JSON.stringify` on an order that holds a BigInt, with and without a replacer.

*[`bigint_conversions_js.js`](examples/bigint_conversions_js.js) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```javascript
// holds a BigInt, with and without a replacer. A thrown error prints as
// name: message.
```

<!-- /output -->

- **A string keeps every digit.** `BigInt("0x1f")` reads the hex prefix and gives `31n`, and `BigInt("9007199254740993")` is exact. ECMA-262 accepts a decimal integer with an optional sign, or a `0x`, `0o` or `0b` literal, optionally with white space around it ([StringToBigInt ↗](https://tc39.es/ecma262/#sec-stringtobigint)).
- **A Number has already rounded.** `BigInt(2 ** 53 + 1)` is `9007199254740992n`: the double was rounded before `BigInt` saw it, and `BigInt` converts the double it gets exactly. That is also why `BigInt(2 ** 64)` has all 20 digits: 2^64 is a double. To get a big integer exactly, parse it from a string ([Parsing numbers](../../10_Numbers_and_Math/parsing_numbers/README.md)).
- **What is not an integer is refused.** `BigInt(1.5)` throws a `RangeError`: a Number must be integral ([NumberToBigInt ↗](https://tc39.es/ecma262/#sec-numbertobigint)). `BigInt("1.5")` throws a `SyntaxError`, because `1.5` is not an integer literal.
- **`BigInt("")` is `0n`**, not an error: in the same grammar, a string of nothing but optional white space has the value 0 ([StringToBigInt ↗](https://tc39.es/ecma262/#sec-stringtobigint)).
- **`JSON.stringify` throws on a BigInt** anywhere in its input ([SerializeJSONProperty ↗](https://tc39.es/ecma262/#sec-serializejsonproperty)). A replacer that turns each BigInt into a string writes all the digits, and `BigInt()` reads them back. The same step looks for a `toJSON` method on a BigInt first, which is another way through, but one that changes `JSON.stringify` for all code in the program. [JSON](../../06_Objects/json/README.md) has the rest of what `JSON.stringify` refuses.

## `asIntN` and `asUintN` put a width back

A BigInt never wraps around by itself. `BigInt.asIntN(bits, x)` and `BigInt.asUintN(bits, x)` make it wrap, as a fixed-width integer would; the last two rows store values into typed arrays, which have a fixed width of their own.

<!-- source:bigint_fixed_width_js -->
*[`bigint_fixed_width_js.js`](examples/bigint_fixed_width_js.js) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```javascript
// BigInt.asIntN(bits, x) keeps the low `bits` bits of x and reads them as a
// signed integer; asUintN reads them as unsigned. The last two rows store the
// same values into typed arrays, which have a fixed width of their own.
const rows = [
  ["BigInt.asIntN(8, 127n)", BigInt.asIntN(8, 127n)],
  ["BigInt.asIntN(8, 128n)", BigInt.asIntN(8, 128n)],
  ["BigInt.asIntN(8, 255n)", BigInt.asIntN(8, 255n)],
  ["BigInt.asUintN(8, 256n)", BigInt.asUintN(8, 256n)],
  ["BigInt.asUintN(8, -1n)", BigInt.asUintN(8, -1n)],
  ["BigInt.asUintN(8, 255n << 2n)", BigInt.asUintN(8, 255n << 2n)],
  ["BigInt.asUintN(64, -1n)", BigInt.asUintN(64, -1n)],
  ["BigInt.asIntN(64, 2n ** 63n)", BigInt.asIntN(64, 2n ** 63n)],
  ["Int8Array.of(255)[0]", Int8Array.of(255)[0]],
  ["BigInt64Array.of(2n ** 63n)[0]", BigInt64Array.of(2n ** 63n)[0]],
];
for (const [code, value] of rows) {
  const text = typeof value === "bigint" ? `${value}n` : String(value);
```

`asUintN(bits, x)` keeps `x` modulo 2^bits, and `asIntN` then reads a result with the top bit set as negative, subtracting 2^bits ([ECMA-262 — `BigInt.asIntN` and `BigInt.asUintN` ↗](https://tc39.es/ecma262/#sec-bigint.asintn)). So 127 fits in a signed byte, 128 wraps to `-128n`, 255 is `-1n`, 256 is `0n` unsigned, and `-1n` is `255n` unsigned. `255n << 2n` computes 1020 exactly, and `asUintN(8, ...)` keeps its low eight bits, `252n`: what storing into a byte does. At 64 bits the same rule gives 2^64 − 1 and −2^63, and a typed array agrees: `Int8Array.of(255)[0]` is `-1`, as `asIntN(8, 255n)` is `-1n`, and `BigInt64Array` stores 2^63 as −2^63. With these two functions, exact int64 or uint64 arithmetic (a 64-bit hash, say) is BigInt arithmetic followed by one call.

## No fixed width does not mean no ceiling

ECMA-262 sets no limit on the size of a BigInt. V8 does. The program builds a BigInt just under 2^30 bits, then asks for one just over.

<!-- source:bigint_ceiling_js -->
*[`bigint_ceiling_js.js`](examples/bigint_ceiling_js.js) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```javascript
// V8 caps the size of a BigInt. `1n << k` has k + 1 bits, so this builds one
// of 2 ** 30 - 64 bits (about 128 MiB of digits) and then asks for one of
// 2 ** 30 + 1 bits. Only the sizes print: a number this long is never printed.
const row = (code, result) => console.log(`${code.padEnd(34)}${result}`);
const k = 2n ** 30n - 65n;

const widest = 1n << k;
row("widest = 1n << (2n ** 30n - 65n)", "built");
row("widest >> (2n ** 30n - 65n)", `${widest >> k}n, so widest has ${k + 1n} bits`);

try {
  const tooWide = 1n << (2n ** 30n);
  row("1n << (2n ** 30n)", `built, ${tooWide > 0n}`);
} catch (error) {
  row("1n << (2n ** 30n)", `${error.name}: ${error.message}`);
}
```

<!-- output:bigint_ceiling_js -->
*Verified output of [`bigint_ceiling_js.js`](examples/bigint_ceiling_js.js) — regenerated by `tools/run_examples.py`, never hand-typed.*


`widest` was built with 1073741760 bits, about 128 MiB of digits, and shifting it right by one less than that leaves exactly `1n`. `1n << (2n ** 30n)` would need 2^30 + 1 bits, and V8 throws `RangeError: Maximum BigInt size exceeded`. So V8's ceiling lies between 2^30 − 64 and 2^30 bits: a little over a billion.

The exact figure is V8's, not the language's, and V8's source calls it "somewhat arbitrarily chosen" ([V8 — `src/objects/bigint.h` ↗](https://github.com/v8/v8/blob/main/src/objects/bigint.h)). On a 64-bit machine it was exactly 2^30 bits until a change in March 2026 lowered it to 2^30 − 64 ([V8 commit 3f5013f ↗](https://github.com/v8/v8/commit/3f5013f6fd674862a1293400555768e9b9006182)), which is why the program measures two sizes that give the same answer on both sides of that change.

## What to do

- Use a BigInt for an integer that can pass 2^53: a 64-bit ID from a database, nanoseconds, a count of cents at scale.
- Parse big integers from strings, `BigInt("9007199254740993")`, never through a Number, which rounds first.
- Convert on purpose where the two types meet: `BigInt(n)` for a Number that is an integer, `Number(big)` when the nearest double is good enough.
- Remember that `/` truncates toward zero, and that dividing by `0n` throws.
- Compare freely with `<`, `>` and `==`, which compare exact values, but never expect `===` to match a BigInt with a Number.
- Send a BigInt through JSON as a string, with a replacer, and read it back with `BigInt()`.
- Use `BigInt.asIntN` and `BigInt.asUintN` when you need int64 or uint64 wrap-around.
- In TypeScript, write `bigint`: tsc stops a mix before it can throw, and refuses `==` against a `number` as well.

<details markdown="1">
<summary><strong>Solution</strong></summary>

<!-- source:bigint_kata_js -->
*[`bigint_kata_js.js`](examples/bigint_kata_js.js) in full — pasted here by `tools/run_examples.py` from the file CI runs.*

```javascript
// Kata solution: the mean of BigInt timestamps, rounded toward zero. Two
// Numbers hide in the obvious version -- reduce's starting 0 and
// values.length -- and either one would throw a TypeError, so both are BigInts.
function mean(values) {
  const total = values.reduce((sum, value) => sum + value, 0n);
  return total / BigInt(values.length);
}

const timestamps = [1790000000000000000n, 1790000000000000001n, 1790000000000000005n];
console.log(`mean of the three timestamps: ${mean(timestamps)}n`);
console.log(`mean of -7n and 0n: ${mean([-7n, 0n])}n`);

const asNumbers = timestamps.map(Number);
const numberMean = asNumbers.reduce((sum, value) => sum + value, 0) / asNumbers.length;
console.log(`the same mean in Numbers: ${numberMean}`);
```
